# 《黄昏居酒屋》状态系统驱动内容规范

> 更新时间：2026-07-16
> 适用范围：`src/assets/character/**`、`src/assets/schedule.yaml` 中的新建与重构内容
> 配套模板：`docs/状态系统驱动节点模板.md`

这份文档描述当前代码已经实现的内容契约。创作者负责写“本节点演什么、玩家如何回应、节点完成后去哪里、产生什么效果”；运行时根据显式出口切换故事、观察、调酒和来访结束状态。

## 1. 核心原则

1. **一个节点只声明一个明确出口。** 新内容统一使用 `exit`，不靠字段组合猜测下一状态。
2. **不同选项必须有不同回应。** 回应优先写在选项的 `script_flow`，简短文本才用 `immediate_response`。
3. **选项与节点效果都采用声明式事务。** 好感度变化写入 `effects`，由运行时保证同一作用域内不重复结算。
4. **剧情资源只描述内容和引用。** 状态切换、调酒判定、奖励入账、日记汇总由系统执行。
5. **稳定 ID 是存档与自动检查的基础。** `event_id`、带效果的选项 `id`、效果 `id` 发布后不要随意改名。
6. **旧字段只为旧资源兼容。** 它们不是新内容格式，也不能继续复制到模板里。
7. **运行时与自动调试共用纯解释器。** UI、无头路径模拟和开发者 Inspector 不得各自发明跳转规则。

## 2. 内容文件职责

每个角色目录通常包含：

- `character_meta.yaml`：角色基础资料与角色级聊天配置。
- `nodes_main.yaml`：正式来访主线。
- `nodes_teaching.yaml`：教学剧情。
- `nodes_chat.yaml`：来访间隙聊天。
- `nodes_hidden.yaml`：隐藏剧情。
- `observations.yaml`：观察点定义。
- `gallery.yaml`：图鉴条目与解锁条件。
- `loot_table.yaml`：角色相关掉落。

全局 `src/assets/schedule.yaml` 只安排某日有哪些客人以及各自从哪个 `start_node` 开始。日程不是剧情跳转表；节点之间的流向必须由节点出口表达。

## 3. 节点正文

主线与教学节点使用 `script_flow`：

```yaml
script_flow:
  - type: env
    content:
      - 门被风推开了一条缝。
  - type: npc
    content:
      - 「今晚还有位置吗？」
  - type: inner
    content:
      - 他像是已经在门外站了很久。
```

`type` 只允许：

- `env`：环境、动作、镜头信息。
- `npc`：客人台词。
- `inner`：调酒师内心。

`content` 可以是一条字符串，也可以是字符串数组。聊天与隐藏节点仍可使用 `atmosphere_lines` + `content` 的轻量正文形式，但它们同样必须遵守显式出口规范。

`trigger_condition` 用于描述节点的进入前提及内容引用：

```yaml
trigger_condition:
  need_event:
    - guest_previous_event
  need_time: any
  need_item: []
```

它不是节点完成后的路由字段，不能替代 `exit`。

## 4. 唯一的节点出口：`exit`

每个新节点必须从下列四种出口中选择一种。

### 4.1 进入下一个剧情节点

```yaml
exit:
  kind: next
  target: guest_next_event
```

`target` 必须是同一角色中存在的节点 ID。

### 4.2 进入观察

```yaml
exit:
  kind: observation
  prompt: 观察他一直护着的左胸口
  continue_node: guest_after_observation
  feature_groups:
    - body
    - carried_item
```

- `prompt`：进入观察时展示的目标。
- `continue_node`：观察结束后的唯一继续节点。
- `feature_groups`：可选，用于限定本次观察关注的特征组。

观察数据本身继续写在 `observations.yaml`，观察出口只负责把剧情送入观察状态并指定返回点。

### 4.3 进入调酒

```yaml
exit:
  kind: mixing
  request:
    mode: normal
    request_text: 调一杯能让他想起归途的酒
    hint: 他反复看着已经失灵的导航。
    preferred_drink:
      id: R001
      name: 未竟的生诞
      formula: [bc01, m04, f03]
  outcomes:
    success: guest_mixing_success
    fail: guest_mixing_fail
```

正式显式调酒出口必须提供非空 `success` 目标。失败行为二选一：

- 提供非空 `fail` 目标，失败后进入该结果节点；此时显式失败目标优先于 `retry_on_fail`。
- 不提供失败节点时，写 `fail: null` 且设置 `retry_on_fail: true`，失败后停留在调酒并要求重试。

调酒请求必须提供：

- 非空 `request_text`；
- 配方表中存在的 `preferred_drink.id`；
- 非空 `preferred_drink.name`；
- 可校验的 `preferred_drink.formula`。

**执行顺序是先播放当前节点的 `script_flow`，再进入调酒。** 因此请求台词、人物犹豫和叙事铺垫应写在调酒节点正文里，而不是假设系统会立即跳过正文。

### 4.4 结束本次来访

```yaml
exit:
  kind: end_visit
```

`end_visit` 只表示当前客人的本次来访结束；它不等于整日结束，也不等于游戏结局。

## 5. 旧字段的唯一兼容边界

运行时只通过 `resolveNodeExit` 读取以下旧资源：

| 旧资源写法 | 解析后的出口 |
| --- | --- |
| 节点级 `next_node` | `exit.kind: next` |
| `trigger_observation` | `exit.kind: observation` |
| `drink_request` + `on_mixing_complete` / `on_mixing_fail` | `exit.kind: mixing` |
| 没有旧出口字段 | `exit.kind: end_visit` |

兼容逻辑只允许存在于这一处边界。故事运行、图检查和状态控制器都消费解析后的 `exit`，不得再次检查旧字段。

对新内容的要求：

- 不新增节点级 `next_node`。
- 不新增 `trigger_observation`。
- 不新增节点级 `drink_request`、`on_mixing_complete`、`on_mixing_fail`。
- 禁止裸写 `mixing:`；它没有兼容语义，会直接报错。
- 不在同一新节点混写 `exit` 与旧出口字段。

注意：选项上的 `next_node` 是正式字段，不属于上述节点级兼容字段。`fallback_node` 仅为历史预留形状；当前校验只容忍空值，拒绝非空目标。

## 6. 选项、分支与不同回应

推荐结构：

```yaml
player_options:
  - id: ask_about_family
    text: 「是在等家人吗？」
    branch_type: flavor
    script_flow:
      - type: npc
        content:
          - 「……算是吧。」
      - type: env
        content:
          - 他的手指在杯沿停了一下。
    impact_log: 温和地追问他的家人

  - id: avoid_the_subject
    text: 「先喝点热的吧。」
    branch_type: flavor
    script_flow:
      - type: npc
        content:
          - 「谢谢。」
    impact_log: 没有继续追问
```

字段规则：

- `id`：选项稳定 ID。选项存在 `effects` 时必填；为了存档、统计和回归测试，建议所有正式选项都填写。
- `text`：玩家看到的选择文本。
- `branch_type`：
  - `flavor`：不同回答通常回到当前节点的共同出口；
  - `plot`：可用选项 `next_node` 进入专属后续；
- `choice`：用于需要逐项查看的选择组；同一节点的选项必须全部为 `choice`，完成当前可用项后走节点出口。
- `script_flow`：完整的选项回应，支持 `env` / `npc` / `inner`。
- `immediate_response`：只适合一句式回应，不与完整 `script_flow` 重复表达。
- `next_node`：该选项回应结束后的专属目标。
- `next_node: null`：该选项回应结束后直接结束本次来访。
- `fallback_node`：历史预留字段，当前纯解释器不会执行非空 fallback；新内容禁止使用，改写为明确的 `next_node` 或节点 `exit`。
- `impact_log`：供日记或回顾使用的选择摘要。
- `condition`：当前只支持 `need_item` 与 `locked_text`。

一个节点仍只有一个 `exit`；选项专属目标是对共同出口的局部分支覆盖。

`branch_type: choice` 的额外约束：

- 不能与 `flavor` / `plot` 混写在同一节点；
- 不能声明自己的 `next_node` 或 `fallback_node`，每次回应后返回选择组；
- 已完成项会禁用；被 `need_item` 锁定的项不计入本次必须完成的数量，避免永久卡死。

## 7. 好感度与可扩展效果

目前已注册的关系轴是 `affection`，初始值为 0，运行范围为 -100 至 100。新内容使用统一效果类型：

```yaml
effects:
  - id: family_question_builds_affection
    type: relationship.change
    target: self
    axis: affection
    amount: 2
    feedback: 他发现你并不是在猎奇。
effect_scope: game
```

规则：

- `id` 在同一个效果块内唯一且非空。
- `type` 当前只允许 `relationship.change`。
- `target: self` 指当前来访角色；也可填写明确角色 ID。
- `axis` 当前写 `affection`。字段虽为扩展预留，但未注册的新轴不能直接投入内容。
- `amount` 必须是有限且非零的数字，可正可负。
- `feedback` 可选，用于向玩家解释这次变化。
- `effect_scope` 只能是 `game` 或 `visit`，省略时默认为 `game`。

作用域语义：

- `game`：同一来源的效果整局只结算一次，适合不可重复的关键选择和剧情完成奖励。
- `visit`：同一来源在同一次来访中只结算一次，下一次来访可以再次发生。

效果可以放在两个位置：

1. **选项 `effects`**：玩家确认该选项时结算，因此选项必须有稳定 `id`。
2. **节点 `on_complete.effects`**：节点正文、选项和奖励展示完成后，在执行出口前结算。

```yaml
on_complete:
  effect_scope: game
  effects:
    - id: understood_his_request
      type: relationship.change
      target: self
      axis: affection
      amount: 4
      feedback: 这杯酒让他觉得自己被理解了。
```

不要在台词里埋“+2 好感度”再让代码猜测；叙事反馈写台词，数值结算写效果。

## 8. 教学、奖励、日记与图鉴

### 8.1 教学

`teaching` 负责配方、步骤和提示；完成教学说明后，用 `exit.kind: next` 进入单独的调酒节点。调酒节点仍遵循“先播放正文，再执行 mixing 出口”。

教学配方的 `recipe.id` 与 `formula` 必须能在配方和材料目录中通过校验。

### 8.2 奖励

奖励统一写入 `reward.details`：

```yaml
reward:
  details:
    type: recipe
    id: R001
    name: 未竟的生诞
    description: 一杯承载未竟心愿的酒。
    quantity: 1
```

`details` 可以是单个奖励，也可以是奖励数组。`type` 只使用 `ingredient`、`item`、`recipe`。

### 8.3 日记

`diary_note` 必须是字符串：

```yaml
diary_note: "他一直护着胸口的盒子，像是在保护最后一次送达。"
```

禁止写成对象、数组或带自定义子字段的结构。玩家选项的 `impact_log` 与结果节点的 `diary_note` 可以共同保留“我做了什么”和“我如何理解这段来访”。

### 8.4 故事与图鉴

节点可声明章节解锁：

```yaml
story_unlocks:
  chapters:
    - id: guest_chapter_01
      reason: 他终于说出了等待的人。
```

`gallery.yaml` 中的 `profile_sections[].unlock_condition` 应引用真实事件或解锁标识。图鉴负责沉淀角色事实，剧情节点负责制造获得这些事实的过程；不要把完整真相提前塞入浅层图鉴。

## 9. 节点执行时序

普通节点的关键时序是：

1. 播放节点正文。
2. 展示并处理玩家选项；选中选项时结算选项效果。
3. 播放该选项自己的不同回应。
4. 展示节点奖励等收尾内容。
5. 结算 `node.on_complete`。
6. 执行节点 `exit`。

因此：

- 调酒请求节点不会跳过 `script_flow`。
- 观察提示应由观察出口提供，而不是靠正文关键字触发。
- 终局奖励、日记和好感度可以放在结果节点，再以 `end_visit` 收束。
- 不要让状态控制器根据 `event_id`、文案、文件名或 `type` 猜测流向。
- `llm_chat.entry_mode: before_next_node` 会被解释为显式 `tail_chat` 指令，并携带精确恢复节点；选项是否有回应文本不再影响尾聊是否触发。
- 教学调酒的 retry-only 失败由解释器保留为“失败 → 重试 → 成功”的可执行路径，不视为结构死循环。

## 10. 自动门禁

提交内容前至少运行：

```bash
npm run content:check
npm run narrative:check
npm run narrative:simulate
```

- `content:check`：检查资源结构、引用、配方、出口、效果、日记等内容契约。
- `narrative:check`：检查日程入口、剧情图、出口目标、调酒分支、不可达节点和其他图结构问题。
- `narrative:simulate`：无 UI 枚举选项、逐项选择、观察、调酒成功/失败与恢复重试、尾聊和来访结束；结构死循环、步数上限、分支爆炸或无法结束会返回失败码。

`dev`、`lint`、`build` 的前置脚本已经串联这三道检查，但内容提交仍应主动运行它们，便于快速定位问题。

常用模拟方式：

```bash
# 全排期，假定条件物品均可用，覆盖最大结构分支
npm run narrative:simulate

# 指定角色和入口，并输出机器可读路径
npm run narrative:simulate -- --guest aqiang --start aqiang_001_dialogue_main --json

# 模拟没有任何条件物品的场景
npm run narrative:simulate -- --day W1_D3 --no-items

# 指定当前可用物品，可重复写 --item
npm run narrative:simulate -- --guest guest_id --item old_ticket
```

默认模拟是结构覆盖，不读取某个真实存档。`--no-items` / `--item` 用于明确选项可用性场景；教学 retry 默认只代表性覆盖一次失败后恢复，可用 `--max-retries` 调整。`--max-paths` 与 `--max-steps` 防止错误内容拖死检查进程。

开发模式的“系统菜单 → 调试跳转”中还提供剧情 Inspector，显示当前状态、节点、声明出口、解释器实际指令、精确关系轴、事实计数与最近事务。复制功能只导出这些白名单剧情字段，不包含 MiniMax Key 或完整游戏上下文。

现有内容仍会报告一批 `UNREACHABLE_MAIN_NODE` warning，主要记录尚未接入日程或未来阶段的主线节点。数量以当前 `npm run narrative:check` 的实时输出为准：

- warning 不会被当成 error，也不会让命令以失败码退出；
- warning 不代表内容已经正确，只表示当前门禁允许带着这份已知清单继续工作；
- 现有 warning 需要保留清单并逐项消化，不能长期把它们当成无须处理的噪声；
- 新增或重构内容不应无解释地扩大 warning 清单；
- 真正的 error 必须在提交前清零。

## 11. 提交前内容自检

- [ ] 新节点都有且只有一个显式 `exit`。
- [ ] 没有新增节点级旧出口字段，也没有裸 `mixing:`。
- [ ] 调酒出口同时提供有效的成功、失败目标。
- [ ] retry-only 调酒使用 `fail: null + retry_on_fail: true`；存在显式 fail 目标时不误以为仍会原地重试。
- [ ] 调酒节点正文会先完整播放，再进入调酒。
- [ ] 不同选项具有不同回应；正式选项有稳定 `id`。
- [ ] `choice` 逐项选择组没有混入其他分支类型，也没有选项级跳转。
- [ ] 没有使用非空 `fallback_node`。
- [ ] 带效果的选项一定有 `id`，效果 `id` 在块内唯一。
- [ ] 好感度使用 `relationship.change / affection`，数值非零，作用域明确。
- [ ] 节点完成效果写在 `on_complete`，不藏在文案或跳转代码中。
- [ ] `diary_note` 是字符串。
- [ ] 奖励写在 `reward.details`。
- [ ] 观察、教学、调酒、奖励、日记和图鉴引用都能落到真实内容。
- [ ] `npm run content:check` 无 error。
- [ ] `npm run narrative:check` 无 error，并审阅 warning 变化。
- [ ] `npm run narrative:simulate` 的全部目标均可结束，且无 unexpected loop、step limit 或 issue。
